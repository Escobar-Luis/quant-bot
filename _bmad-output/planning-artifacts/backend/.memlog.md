- (version) Measured 2026-10-17 on Luis's Mac with warm bars: LPP v1 build 0.06 s + 315 positions simulate at one delay 0.21 s; Crypto Wizard 126 positions 0.55 s. data/bars is 94 MB (alpaca_1m 21 MB, binance 71 MB). On-demand runs fit a synchronous request.
- (decision) Paradigm: snapshot serving. Pipelines (pipes and filters) on Luis's Mac write immutable versioned snapshots; one stateless API serves them and runs the same engine on demand behind a content-addressed cache. Binds all units; prevents the API and pipelines each owning data.
- (decision) Files are the source of truth: a snapshot = results/<course>/<version>.json (results/1, unchanged) + derived events + manifest; only pipelines write; API read-only; live by flipping one pointer. Trade-off: no ad-hoc queries without a read model, but auditable, diffable, rebuildable, matches the frozen demo contract.
- (decision) Databases are derived read models only (SurrealDB from PR #11 or any other), rebuilt from a snapshot, never on the verdict or run path. Trade-off: two stores to keep in step vs a DB outage never breaking verdicts. Open for Luis: keep SurrealDB as read model, drop it, or make it the store.
- (decision) One engine: API runs call one shared function extracted from backtest.run (CLI and API both thin callers); the word only from engine.word. Prevents API numbers drifting from nightly numbers.
- (decision) On-demand run = canonical RunSpec {course, version, delay_min 1..60, start, end, portfolio}; key = sha256(spec + snapshot_id + engine_version); immutable results, never invalidated (new snapshot or engine = new key). Specs equal to a precomputed one are served from the snapshot.
- (decision) Request path never fetches bars from the network: bars come from the snapshot's bar store (what the nightly run used); a miss prices as no_bars and lands in unknown. Prevents IEX vs SIP drift, key burn and unbounded latency on public traffic.
- (decision) Runs are synchronous (0.3-0.6 s measured) in a small worker pool: global concurrency 2, 10 s timeout, 429 with Retry-After beyond. No job queue until a run exceeds ~5 s. Trade-off: simplest correct vs no progress UI for long runs.
- (decision) Auth: Clerk session JWT verified networklessly on the API (JWKS or PEM, azp allowlist). Public: health and verdict reads (Decision 3: everyone sees the same verdicts). Signed in: runs and picks. Identity = Clerk user id only; we store no email or name.
- (decision) Per-user picks [ASSUMPTION, ask Luis]: Clerk publicMetadata.course_picks, written only by our API after validating course ids; no user table of ours. Trade-off: zero DB vs can't query across users and Clerk API rate limits.
- (decision) Tracing: every API-triggered compute (cache miss) = one PRISM trajectory, new agent_id daytrader-api-backtest-v1 (AGENTS.md PR first), conversation_id api-<course>-<key12>, tool_call steps, final_answer last, final_status error naming the failed check, locators only, user as salted hash. Submitted after the response from a bounded in-process queue; PRISM down never fails a request. Cache hits are not runs, not traced.
- (decision) Cost: API makes no model call on the request path; verdict text for custom runs is code-templated from run numbers. Model calls live in nightly pipelines: temperature 0 + versioned prompts so Nicrron's free exact cache (X-Nicrron-Cache: HIT) makes re-runs free; first line is our own idempotency ledger per (source_id, model, prompt_version).
- (decision) Rate limits: in-process token buckets: public reads 60/min per IP, runs 10/min burst 5 per user, global daily compute cap (RUNS_PER_DAY) that also caps PRISM credits; Nicrron client bucket 50/min with backoff on 429/502, streaming for long calls; nightly spend cap NIGHTLY_BUDGET_USD.
- (decision) Nightly pipeline runs on Luis's Mac (launchd), not the server: raw course content never leaves the Mac (rule 5) and Discord is read in his signed-in Chrome, supervised (rule 6). Stages: collect new, extract (idempotent), code checks, backtest all delays, build snapshot, validate, publish, flip pointer. Any failure keeps the previous snapshot live.
